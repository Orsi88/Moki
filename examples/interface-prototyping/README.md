# Example: interface-prototyping

Synthetic project: Acme Library. Ask Artesão: "Build a local, self-contained HTML prototype for staff reservations: search/filter a list, open a details modal and submit a reservation form. Include success and validation-error states. Use explicit synthetic data, no real API, no new dependency."

Supply a small visual reference with type/spacing/color conventions and a long book title. Request the HTML only. Browser review captures, if available, are working material rather than extra deliverables.

## Acceptance checklist

- [ ] Reuses the reference direction and owns routine composition/formatting choices without asking about each pixel.
- [ ] Delivers a runnable HTML file; the agreed filtering, modal, form validation and success interaction work.
- [ ] Makes synthetic data and simulated persistence/integration boundaries clear.
- [ ] Handles long text, empty filter results, a narrow viewport and normal desktop layout without unacknowledged clipping.
- [ ] Uses meaningful labels/native controls and verifies keyboard/focus handling, including modal opening, closing and focus restoration when supported.
- [ ] Actually opens and exercises the result when a browser is available; otherwise reports that visual/interaction verification was unavailable.
- [ ] Does not claim full accessibility or real backend verification from automated checks or a mock.
- [ ] Delivers only the HTML; no screenshot pack/PDF or unsolicited framework installation, deployment or real form submission.

## Existing-project variant

Supply an existing UI repository with local uncommitted edits and ask for the same flow.

- [ ] Inspects the current design system and proposes the target edits before changing them; preserves unrelated/manual work and existing tooling.

This is an acceptance scenario, not a recorded passing browser pilot.
